# Prior art shapes distlayout's two-level nested layout

**Bottom line.** No surveyed system does everything distlayout's two-level layout (L3->L2 per `air.segment`, L2->L1 per herd PE, nothing inside L1) needs, but the pieces exist and point in one direction: keep a **uniform, formula-style layout per level** (CuTe/DISTAL/Shardy), allow **per-outer-piece heterogeneity only as an explicit override keyed by the outer piece** (the HTA-of-HTAs and Legion region-tree pattern), and add a **static per-level byte fit check**, which none of Sequoia, Legion, DISTAL, Fireiron or Exo performs ([Fatahalian et al. 2006](https://lph.ece.utexas.edu/merez/uploads/MattanErez/sc06_sequoia.pdf), [Hagedorn et al. 2020](https://arxiv.org/pdf/2003.06324v1)). MLIR-AIR's rules decide the rest: herd and segment sizes must be `arith.constant` by the time `air-to-aie` runs, a herd body is SPMD and cloned per tile, a segment grid stamps out identical bodies with X-only unroll, and a segment allocates L2 (space 1) or L1 (2) while a herd allocates and touches only L1 (checkout `mlir-air` d8d262b: `AIRDialect.cpp:2143-2151`, `AIRToAIEPass.cpp:329-371, 780-841`, `AIRDialect.cpp:1715-1834`). Those rules make "any layout per piece" expensive in practice (one `aie.device` per segment, one `scf.if` arm per class per core, channel balance across arms), so the inner layout should be **a small set of classes with an escape hatch**, not a free-for-all. On the real NPU numbers (64 KB per compute tile, 512 KB per memory tile, one per column, [arXiv 2512.13282](https://arxiv.org/pdf/2512.13282)), a 1024x1024 fp32 tile over-fills L2 by 8x and a 256x256 fp32 stencil tile with halo over-fills it even single-buffered, so the fit check must count buffer depth, halo and reserved stack, and report the minimal split factor rather than a bare pass/fail. A tree data structure is the right *model* for ownership and local-index queries, but it should be a two-tier record (outer map plus a per-piece inner map), not a general-depth tree.

The column that matters most is the fifth: **only the cost-model mappers do a static fit check**, and they do it over a closed search space (Timeloop rejects a mapping with "mapped tile size 428201 exceeds buffer capacity 65536"; CoSA bounds the log-utilisation of each buffer by log capacity as a MIP constraint). Every programming model leaves capacity to a tunable, a mapper, or a runtime failure. Fireiron states the premise distlayout can build on: the decomposition determines "how many elements of each operand are stored at which layer of the memory hierarchy, (which determines the overall memory consumption)" ([arXiv 2003.06324](https://arxiv.org/pdf/2003.06324v1)). A layout object that knows the bytes per piece per level can therefore check the fit before any compiler sees it, which would be new relative to every surveyed system.

Two rows are weaker than they look. Graphene (Hagedorn et al., ASPLOS 2023) could not be fetched; its tensors-of-tensors notation is reported here only secondhand through LEGO and is **unverified**. "PartTensor" and "Spensor" do not surface under those names in any public source outside this repo's README; the nearest public matches are Vaidya et al., "Distributed Sparse Tensor Computations in MLIR" (LLVM-HPC 2025) and Wang et al., [arXiv 2510.14871](https://arxiv.org/abs/2510.14871v1), neither of whose public text describes the partition encoding, so they are omitted from the table.

## What each system is good at, and the one idea to borrow

**Sequoia** is the cleanest statement of the "inner nodes chop, leaves compute" discipline: "the Sequoia language does not permit inner tasks to directly perform computation on array elements" and "computational kernels are constrained to operate upon data located within leaf nodes of the machine tree" ([SC06 PDF](https://lph.ece.utexas.edu/merez/uploads/MattanErez/sc06_sequoia.pdf)). Its mapping file separates the algorithm from per-level sizes: porting matmul from Cell to a cluster changed only the leaf kernels and the tunables (U=X=V=1024 at cluster level, 128 at node level, 32 at L2). Its `rchop`/`ichop`/`gather` primitives are the same three decomposition kinds distlayout already has (regular block, uneven block, index list). Borrow: the rule that nothing lives below the leaf level (distlayout's "nothing inside L1"), the idea of *virtual levels* so a non-tree fabric (a 4-column NPU where columns can borrow each other's memory tile) can still be modelled as a tree, and the sizes-live-outside-the-algorithm split. Do not borrow the one-instance-per-level restriction, which is exactly what blocks per-sibling heterogeneity.

**Legion** is the only system with direct evidence of sibling pieces partitioned differently: `p_nodes_pvs[0]` is partitioned by `node_owner_map`, `p_nodes_pvs[1]` by both `node_owner_map` (disjoint) and `node_neighbor_map` (aliased), "two views on to the same collection of data" ([Bauer et al. 2012](https://legion.stanford.edu/pdfs/sc2012.pdf)). Its dependence analysis is O(d) in tree depth, so depth is unbounded by design. Borrow: any piece may be re-partitioned with its own functor, and every partition carries a disjoint/aliased bit so halos are expressible. Memories, however, are a mapper-queried graph, not part of the data model; the mapper returns "a prioritized list of memories" and the runtime tries them in order. That split (layout says *what*, a separate placement step says *where*) is right for a library, but distlayout's levels are tied to memories by construction, so the placement step is fixed and the capacity check can be done up front.

**Chapel** contributes closed-form owner and local-index queries (`localSubdomain()`, `targetLocales()`, the block-cyclic owner formula j_k = ((i_k - s_k)/b_k) mod N_k) ([BlockCycDist](https://chapel-lang.org/docs/modules/dists/BlockCycDist.html)) and a hard two-level limit in its GPU model: "neither GPU locale has GPU sublocales of its own" and "Distributed arrays cannot be used inside GPU kernels" ([GPU technote](https://chapel-lang.org/docs/technotes/gpu.html)). That is the same shape as distlayout's model: distribution stops at the device level, and inside it the code is placement by nested `on`, not a layout. Borrow: the query API, and the precedent that a fixed depth of two is a defensible design.

**DISTAL** gives the best surface notation for a nested layout list: `[T xy->xy M, T zw->z M]` is "a two dimensional tiling of a matrix at the outer level, and row-wise partition of each tile for each GPU", and the machine is recursive ("each abstract processor may itself be viewed as a distributed machine") ([arXiv 2203.08069](https://arxiv.org/abs/2203.08069)). The distribution is part of the tensor *format*, separate from the schedule. Borrow: one distribution per level, written as a list, with the inner one applied to each outer piece's index space. Its limit is instructive: one statement per level means every outer tile gets the same inner split, and the authors say outright that recursive algorithms like CARMA cannot be represented.

**HTA** is the one layout system whose *object* is hierarchical: "tiles can be either conventional arrays or lower level Hierarchically Tiled Arrays", built from explicit partition vectors (`hta(M, {[1 3 5],[1 3 5]}, [2,2])`) or as "an empty set of tiles" whose content is assigned per tile ([PPoPP 2006 PDF](https://www.lrde.epita.fr/~bleton/doc/bikshandi06programming.pdf)). Its access syntax separates levels cleanly (`C{2,1}` tile, `C{2,1}{1,2}(1,2)` element, `C(5,4)` flat). Borrow: partition vectors as the representation for uneven outer tiles (this is what `UnevenBlock` in `distlayout/decomposition.py` already is), and the four access forms as the query API. The price HTA pays is that it has no algebra: no inverse, no complement, no static check, only access syntax and bulk operators. Note also that the C++ `HTA<double,2,LEVEL>` form is uniform per level, so even HTA retreated to uniformity when it needed a static type.

**CuTe** is the algebra. A layout is a shape tree with strides; nesting is tuple nesting; division is composition with the tiler and its complement, `A / B := A o (B, B*)`, and `zipped_divide` returns `((TileM,TileN),(RestM,RestN,...))`, where the tile mode is the local-index map and the rest mode is the ownership map ([02_layout_algebra](https://github.com/NVIDIA/cutlass/blob/main/media/docs/cpp/cute/02_layout_algebra.md)). Borrow: the idea that owner and local index fall out of *one* definition and that complement derives the "rest" automatically, which makes gather and inverse mechanical in the uniform case. CuTe requires divisibility and documents no partial tiles in the pages read; it has no memory levels and every tile shares the tile-mode layout.

**LEGO** shows how to live without explicit strides ("derives the strides internally from the hierarchical tiling specification") and how to handle ragged edges: `ExpandBy` widens to an expanded space and indices outside the original extents return -1, "a similar approach to the oversampling method in CuTe" ([arXiv 2505.08091v2](https://arxiv.org/html/2505.08091v2)). Its `GenP` level accepts any user bijection, with the inverse "left as user's responsibility". Borrow: the -1-outside-the-extent rule for uneven tiles, and the warning implicit in `GenP`: an opaque per-piece function costs you the inverse and the checks.

**Fireiron** fixes three memory levels and four compute levels and makes each decomposition step a typed transition: `MatMul(M,N,K)(GL,GL,GL)(Kernel)` becomes `MatMul(128,128,K)(SH,SH,GL)(Block)` after `.tile(128,128).to(Block).load(A,SH,_)`, so "a level's output is the next level's input problem" ([arXiv 2003.06324](https://arxiv.org/pdf/2003.06324v1)). Borrow: the residual-problem view (the segment-local index space is the input to the herd layout) and the observation that the decomposition fixes bytes per level.

**Exo** has no hierarchy at all, only named memories (`@DRAM`, `@SCRATCHPAD`) and moves as scheduling operations (`stage_mem`); memory annotations are "ignored during scheduling" and checked only "immediately prior to code generation" ([PLDI 2022 PDF](https://cap.csail.mit.edu/sites/default/files/research-pdfs/Exocompilation%20for%20Productive%20Programming%20of%20Hardware%20Accelerators.pdf)). Borrow: the memory tag on a buffer is a type, and its consistency is a back-end check; capacity is encoded as `assert m <= 16` preconditions on instruction shapes, which is what distlayout's fit check generalises.

**Triton** binds levels to hardware names (register/lane/warp/block) and defines what happens when the layout and tensor sizes disagree: larger tensors wrap so each thread owns several values, smaller ones broadcast so "each value is owned by multiple threads" ([TritonGPUAttrDefs.td](https://raw.githubusercontent.com/triton-lang/triton/main/include/triton/Dialect/TritonGPU/IR/TritonGPUAttrDefs.td)). Its `LinearEncodingAttr` requires bijectivity after removing broadcast bases. Borrow: the explicit wrap/broadcast semantics for replication, and the bijectivity rule as the correctness condition the fit check should also verify.

**Shardy/GSPMD** is the degenerate flat case distlayout must reproduce exactly when every segment shares an inner layout: a per-dimension major-to-minor list of mesh axes, `sharding<@mesh, [{"x"}, {"z","y"}]>`, with sub-axes `"x":(m)k` and padding when the axis product does not divide the dimension ([sharding representation](https://openxla.org/shardy/sharding_representation)). There is no place in the representation for per-device variation. Borrow: nothing new, but use it as the conformance target for the uniform path.

**Timeloop/CoSA** give the fit check its vocabulary. Timeloop's tile size at a level is the product of loop factors at that level and below, projected per data space, with halo included for inputs (N*C*(S+(Q-1)*stride)*(R+(P-1)*stride)), bypassed tensors not counting against the level, and the error reporting needed versus capacity ([timeloop issue #23](https://github.com/nvlabs/timeloop/issues/23)). CoSA adds per-tensor per-level utilisation, a precision term, and a soft objective (geometric mean of utilisation) on top of the hard bound ([CoSA](https://arxiv.org/html/2105.01898v1)). Borrow: the report format, the halo formula, bypass, and the distinction between hard verdict and soft score.

**MLIR-AIE/AIR practice** supplies the ground truth on what "fits" means on the NPU and what the compiler does about it, covered in the next two sections.

## MLIR-AIR's structural rules fix what the inner layout may be

All citations in this section are to the local checkout `/uufs/chpc.utah.edu/common/home/u1418973/other/spatialAIR/mlir-air` at d8d262b ("spatialair" fork, 2026-11-02); TD = `mlir/include/air/Dialect/AIR/AIR.td`, DIALECT = `mlir/lib/Dialect/AIR/IR/AIRDialect.cpp`, TOAIE = `mlir/lib/Conversion/AIRToAIEPass.cpp`, CM = `docs/AIRComputeModel.md`, DSL = `python/air/api/`.

**Static bounds.** At the dialect level all three ops take `Variadic<Index>:$sizes` and no verifier checks for constants (TD:163, 257, 384; DIALECT:936-938, 1832-1834, 2153-2157), and region invocation bounds are explicitly "Unknown" when a size is non-constant (DIALECT:955-975). But every AIE-side consumer hard-requires constants: `HerdOp::getNumCols()/getNumRows()` do an unchecked `cast<arith::ConstantIndexOp>` on `sizes[0]` and `sizes[1]` (DIALECT:2143-2151), called from `air-to-aie` (TOAIE:334-335, 6116-6117) and `air-place-herds` (`AIRHerdPlacementPass.cpp:217-218`); `getSegmentUnrollFactors` errors with "segment unroll X-dimension size must be a static constant" (TOAIE:780-824) and rejects any Y unroll above one, "AIE only supports column-wise device slicing" (TOAIE:829-841). Launch sizes are the only ones `air-to-aie` never reads; the launch body runs on the host (CM:33-35). The Python DSL never emits a symbolic bound: `parse_grid` accepts only `range`, `product(range)` or a list of ranges with uniform stride (`_trace.py:694-726`), so every grid is a compile-time integer tuple. Consequence for distlayout: a nested layout targeting AIR must have **integer outer and inner piece counts**; symbolic counts are legal in the IR but dead on arrival at `air-to-aie`. A 1-D herd is also unsafe (`getNumRows()` indexes `sizes[1]` out of range), so write `(N,1)` or `(1,N)`.

**SPMD body and branch-per-class.** Each op has exactly one region (TD:172, 266, 392). `outlineAIECores` clones the herd body once per tile at `(x + col_offset, y + row_offset)` (TOAIE:329-371), so every PE runs the same body parameterised by `%x,%y` (CM:603-612). Per-tile divergence is expressed only by control flow on the ids: `ops.branch(cond)` builds `scf.if` (or `affine.if` on spatial targets) and accepts only "a comparison between index expressions, such as `tx == 0`" (`_cond.py:363-400, 633-643`); `air-specialize-dma-broadcast` emits `affine.if` dispatch on herd-id dimensions (`AIRMiscPasses.cpp:194-202, 324-325`); `air-to-aie` lowers `scf.if`/switch arms inside cores under the "only one arm runs per dispatch" assumption (TOAIE:3622-3760). Because the tile ids become constants after outlining, an `scf.if` on them resolves statically per core, which is what makes branch-per-class work. The constraint that bounds it is channel balance: "Along every possible execution path ... the number of put operations and the number of get operations at each channel index must be equal," per iteration inside loops (CM:791-800). A per-class arm with a different number of DMA transfers is therefore only safe in the specific dispatch shapes `air-to-aie` knows. A segment grid is stricter still: "every point in the space instantiates an independent copy of the segment body" (CM:349-359), so a segment iteration space cannot carry per-point different bodies; different bodies need separate `air.segment` ops, each of which becomes its own `aie.device` named `<segment>_<ux>_<uy>` (TOAIE:1696-1780). Multiple herds in one segment land on one device and are placed as independent rectangles by `air-place-herds` (`AIRHerdPlacementPass.cpp:197-250`), which fails with "No valid placement found." (`:591-594`).

**Memory spaces.** L3=0, L2=1 ("memory tiles"), L1=2 (CM:48-52); "Direct reads or writes across levels ... are not supported" (CM:54-56). `verifyAllocMemorySpace` gives a segment a minimum of L2 (so L2 or L1 allocs) and a herd a minimum of L1 (DIALECT:1715-1764, 1832-1834, 2153-2155); `verifyComputeMemoryAccess` rejects any load/store inside a herd below L1 with "AIE core tiles can only access L1 or more local memory directly" (DIALECT:1789-1830). The same `air.dma_memcpy_nd` / `air.channel.put/get` ops express L3->L2 and L2->L1; the level is inferred from the memref spaces (TD:489-527, 782-810, 978-997; CM:891-896). A segment may not mix `dma_memcpy_nd` and channels (TOAIE:4070-4082). The DSL exposes three allocation scopes: `<herd>.private()` is L1, `<segment>.private()` is L2, `<segment>.shared()` is L1 with segment lifetime; there is no `<herd>.shared()` (`_trace.py:2056-2075`).

**Placement.** Herd and segment carry `x_loc/y_loc` (TD:294-311, 422-423); physical tile = `(x_loc + %x, y_loc + %y)` (CM:652-654; TOAIE:344-371). The DSL defaults are `PHYSICAL_HERD = {"npu1": {1: (4,), 2: (1,4)}, "npu2": {1: (8,), 2: (2,4)}}`, bounded by shim-DMA capacity: "npu1 routes 4 cores and npu2 routes 8; 16 cores fails placement with 'no ShimNOCTile has sufficient DMA capacity'" (`_trace.py:83-97`). `air.herd(iterable, shape=, at=)` strip-mines the logical grid onto `shape`, and "each dimension must strip-mine exactly" (`_trace.py:1371-1400`). L2 allocs are bucketed by shared channel and assigned to memory tiles round-robin, with `air.memtile_col` as a pin (TOAIE:2613-2640, 2633-2790); the only "budget" there is `kBucketsPerMemtileBudget = 1`, a lock-count heuristic, not bytes (TOAIE:2707-2820).

**Capacity.** No byte-level L2 check exists in `mlir/lib`; grepping for capacity finds only shim-DMA pressure (`AIRDmaToChannel.cpp:1712-1726`) and the L1 `exceedsL1Budget` check in the ping-pong pass, active only when a device is named (`AIRDependencyScheduleOpt.cpp:1697-1711, 4076-4089`). The DSL checks at trace time with `L1_BYTES = 65536` per core and an **aggregate** L2 cap of `L2_BYTES_PER_MEMTILE * DEVICE_COLUMNS[target]` = 512 KB x 4 (npu1) or x 8 (npu2) (`_trace.py:109, 125-126, 2179-2190`), so a single 1 MB buffer passes the DSL on npu1 and fails later in mlir-aie's allocator. The docs nevertheless state the intent: "The compiler must determine the total resource requirements of a segment statically" (CM:382-383). The per-memory-tile check (512 KB) and per-core check (64 KB) live in `aie-assign-buffer-addresses` in mlir-aie, which the notes did not read; that error reads "could not be placed: <what> needs N bytes and this tile has no room left for it" and warns that bytes "may well exist while being too fragmented to use" ([core data memory guide](https://xilinx.github.io/mlir-aie/dev/programming_guide/core_data_memory/)).

**What is expressible today versus needs AIR changes.** Expressible with no AIR change: a different inner layout per segment (one `air.segment` per class, each with its own L2 allocs, DMA pattern and herds, at the cost of one device image per segment and multiplying packet ids and locks, which the DSL caps "at about four launches", `_compile.py:366-373`); a different herd shape per segment or several herds of different shape in one segment (`shape=`, `at=`); per-core different L2->L1 extents inside one herd via `ops.branch(tx == ...)`, subject to channel balance; and uneven edge tiles via `ops.branch` on launch/segment ids or by padding. Not expressible without AIR changes: symbolic herd or segment sizes on AIE; row-wise segment unroll; a segment that uses DMA for L3->L2 and channels for L2->L1; per-memory-tile byte accounting inside AIR (the `memtile_col` pin controls placement but checks nothing); 1-D herds. One gap to flag: the notes found no verifier for the documented nesting rule (segment inside launch, herd inside segment; CM:558-562), so it is a convention enforced by passes, not by `verify()`; and whether two `segment()` contexts inside one DSL `launch()` are accepted at the trace level is **unverified** (the IR and `air-to-aie` handle it).

## A tile that does not fit L2 is the common case, not the edge case

The real numbers are small. Both XDNA generations have **64 KB of data memory per compute tile and 512 KB per memory tile**, one memory tile per column; compute and shim tiles have two MM2S plus two S2MM DMA channels, memory tiles six plus six; shim tiles hold at most 16 buffer descriptors; compute and shim DMAs address 3-D, memory-tile DMAs 4-D ([arXiv 2512.13282](https://arxiv.org/pdf/2512.13282)). The 64 KB is organised as eight 8 KB banks interleaved into four 16 KB banks for the programmer, and each tile can also address three neighbours' memory for 256 KB total ([AM020](https://docs.amd.com/r/en-US/am020-versal-aie-ml/AIE-ML-Array-Features), [UG1603](https://docs.amd.com/r/2024.1-English/ug1603-ai-engine-ml-kernel-graph/AI-Engine-ML-Memory)). Usable L1 is less than 64 KB: the stack, `aie.buffer`s and the program's static data share it, with a 1024-byte default stack reservation ([core data memory guide](https://xilinx.github.io/mlir-aie/dev/programming_guide/core_data_memory/)), and the GEMM paper budgets 63 KB. For comparison, a Cerebras PE holds 48 KB for code and data together ([Cerebras](https://www.cerebras.ai/blog/an-ai-chip-with-unprecedented-performance-to-do-the-unimaginable)), and a TPU v4 TensorCore has 16 MiB of VMEM ([arXiv 2304.01433](https://arxiv.org/pdf/2304.01433v1)); the NPU's L2 is 32x smaller than that and its L1 256x smaller.

Three worked examples (arithmetic is the notes' own; capacities cited above). A **16x16 fp32 tile is 1 KiB**; with two inputs and one output at depth 2 it is 5 KiB and fits every level everywhere. A **1024x1024 fp32 tile is 4 MiB, eight times one memory tile**; Timeloop would print "mapped tile size 1048576 exceeds buffer capacity 131072" in 4-byte entries. The responses that actually appear in practice: split 8-way into 128x1024 panels of exactly 512 KiB, which is precisely the L2 panel `memref<128x1024>` in AIR's GEMM case study, and then split again 4-way with `air-split-l2-memref` into `memref<32x1024>` "to adhere to AIE memtile-specific buffer and DMA channel constraints", fuse to `memref<32x256>` (32 KiB) with `air-loop-fusion`, and ping-pong on a 256x32 chunk with `air-ping-pong-transform` ([GEMMCaseStudy.md](https://github.com/Xilinx/mlir-air/blob/main/docs/GEMMCaseStudy.md)); or stream over K in 256-row chunks; or drop to bf16 (2 MiB, still 4x over, then split 4-way). On a 64 KB core the same tile needs 64 splits to reach AIR's per-core 32x32 fp32 = 4 KiB block before any double buffering. The **3x3 stencil on a 256x256 fp32 tile** is the instructive one: the haloed input is (256+2)^2 x 4 B = 266,256 B, about 260 KiB, plus a 256 KiB output = **516 KiB, over the 512 KB memory tile even single-buffered**; with ping-pong on the input it is 776 KiB. On a core, a 64x64 fp32 input with halo (66x66 = 17 KiB) at depth 2 (34 KiB) fits only if the output is single-buffered (16 KiB), 50 KiB total, 79% of the budget. Timeloop's input-tile formula with the `(S+(Q-1)*stride)` term is exactly this halo accounting ([timeloop issue #23](https://github.com/nvlabs/timeloop/issues/23)).

The catalogue of responses across systems, from the notes, is wider than "split":

Two points from the GEMM paper change what "fit" should mean. First, its L1 constraint is an explicit formula, 2*m*k*ty(A) + 2*k*n*ty(B) + m*n*ty(C) <= 63 KB, solved exhaustively by maximising m*k*n then minimising m*n, and the chosen int8 kernel 64x232x64 uses 62.0 KB, 97% ([arXiv 2512.13282](https://arxiv.org/pdf/2512.13282)). Second, filling the level is not the goal: "when further increasing the product of m_ct*n_ct (thus decreasing k_ct to fit in L1), GEMM performance on NPU array drops". In AIR practice L2 sizing is also gated by DMA channels, BD counts and 4-D addressing as much as by bytes; `air-split-l2-memref` and `air-unroll-outer-affine-loops` exist for channel and BD limits, not capacity.

The recommended fit-check report for distlayout, synthesised from Timeloop's error, CoSA's per-tensor utilisation, the GEMM paper's Eq. 5, MLIR-AIE's fragmentation note and Triton's required/limit pair, is: per level, `bytes_available` (raw capacity minus reserved stack, static data and pinned buffers), `bytes_needed` as the sum over tensors of elements including halo and padding times dtype bytes times buffer depth, a per-tensor breakdown, and utilisation; which tensors bypass the level or borrow from a neighbour, and bank and alignment constraints (16 KB banks on the core, 128-bit rows on the memory tile); the resource counts that also gate a split (2+2 DMA channels on core and shim, 6+6 on the memory tile, 16 BDs per shim, 3-D vs 4-D addressing); and, on failure, the minimal split factor `ceil(needed/available)` per candidate dimension, the effect of dropping depth from 2 to 1, the effect of changing dtype, and whether the shortfall is fragmentation rather than bytes. Alongside the hard verdict, a soft score, because Halide, Interstellar and the GEMM paper all show that "fits" and "fast" diverge. This is more than any surveyed system reports, and it is computable from the layout alone.

## A small set of inner classes with an override, not a free-for-all

The AIR rules and the prior art give the same answer from opposite directions. On the AIR side, each distinct inner layout costs something concrete: a distinct **segment** costs one `aie.device`, its own runtime sequence and a multiplication of packet ids and locks (TOAIE:1696-1780; `_compile.py:366-373`); a distinct **branch** inside a herd costs one `scf.if` arm per class, cloned into every core, with channel balance required across arms (CM:791-800) and lowering supported only for the "one arm per dispatch" shapes (TOAIE:3622-3760); and the DSL's `ops.branch` condition must be an index comparison on tile or launch ids (`_cond.py:368-373`), so a class must be nameable as a predicate on the outer piece id. A free-for-all, where every outer piece may carry an arbitrary inner layout, therefore degenerates either into N segments (N devices) or into an N-arm switch in every core, and the fit check, owner and inverse all become per-piece table lookups. On the prior-art side, every system that has an algebra (CuTe, LEGO's `RegP`, Triton, Shardy, Chapel, ScaLAPACK) is uniform, and the two that permit heterogeneity pay for it: HTA's MATLAB form has no inverse or static check, and LEGO's `GenP` leaves the inverse "as user's responsibility" ([arXiv 2505.08091v2](https://arxiv.org/html/2505.08091v2)). Legion shows the heterogeneous form is useful (private/shared/ghost), but Legion has no layout algebra either; it has a runtime.

The recommendation is a **two-tier object with classes**: a uniform inner layout shared by all outer pieces as the default (this reproduces Shardy's flat list and DISTAL's `[outer, inner]` exactly), plus an optional override map from outer piece id to inner layout, drawn from the library's existing layout kinds (block, uneven block, cyclic, index list) rather than arbitrary functions. The number of *distinct* inner layouts, not the number of pieces, is the quantity to keep small, because it is exactly the number of segments or branch arms AIR will emit. Two patterns cover what the notes found a need for: an **edge class** (the ragged last piece along an axis gets a smaller inner split; HTA's partition vectors and LEGO's -1-outside rule), and a **role class** (interior versus boundary pieces in a stencil, Legion's disjoint versus aliased partitions). Anything beyond that should be expressible but visible: the layout should be able to report "this nested layout has k inner classes; on AIR that is k segments or a k-arm branch", so the cost of heterogeneity is a number the user sees before codegen. This is also where the fit check pays off: per class, not per piece, and with the class predicate available for the `ops.branch` condition.

## Use a tree as the model, a two-tier record as the data structure

Sequoia, Legion and HTA all represent nesting as a tree, and for good reason: ownership is a path from root to leaf (segment, then PE), local index is the coordinate at the leaf, and gather is a traversal of the rest mode under one node. Depth, however, is the design choice. Legion's analysis is O(d) and its evaluation uses a three-level AMR code ([Bauer et al. 2012](https://legion.stanford.edu/pdfs/sc2012.pdf)); Sequoia used two levels on Cell and four on the cluster ([SC06 PDF](https://lph.ece.utexas.edu/merez/uploads/MattanErez/sc06_sequoia.pdf)); DISTAL's machine is recursive but was evaluated at two; Chapel's GPU model and Fireiron fix the depth outright. Every tree-general system was exercised at two to four levels, and the host-to-device-local split is the common case. distlayout's hierarchy is fixed by AIR at exactly two memory crossings with nothing below L1, matching Sequoia's "leaves compute" rule and Chapel's "no sublocales of a sublocale".

So the data structure should be a **tree of depth two by construction**: an outer layout (which segment owns a global index, and the segment-local index space), and for each outer piece an inner layout over the herd's PEs (which PE owns a segment-local index, and the PE-local index), with the inner layout stored once when uniform and per piece only in the override map. This is HTA's "tile may be an HTA" flattened to one level and Legion's "partition each subregion with its own functor" restricted to one re-partition. The reason not to build a general-depth tree is the same reason not to allow a free-for-all: every query the user needs (owner, local index, inverse, gather, fit) is a two-step composition when depth is two and uniform, which is CuTe's `zipped_divide` applied twice, and becomes a traversal with per-node dispatch only on the override path. Keep CuTe's integer-function view so the uniform case has an inverse for free; keep a disjoint/aliased bit per level (Legion) so halos at the L3->L2 crossing are representable; store uneven outer pieces as cut points (HTA partition vectors, the existing `UnevenBlock`) rather than as padding, because AIR cannot stamp out uneven copies of a segment body and the branch predicate needs the explicit piece boundary. A general tree can be grown later from this record if AIR ever gains a third crossing; nothing in the surveyed literature argues for building it first.

## Conclusion

The literature splits into systems that have an algebra and are uniform, and systems that permit heterogeneity and have no algebra; distlayout can have both only by making heterogeneity a bounded, explicit override on top of a uniform core, and MLIR-AIR's cost model (one device per segment, one branch arm per class, channel balance across arms) is what sets the bound. The genuinely new contribution available here is the static per-level fit report: none of the programming models does it, the cost-model mappers do it only inside a search, and the NPU's 64 KB / 512 KB levels make it the first thing a user of a nested layout needs to know. Fireiron's observation that the decomposition fixes the bytes at each level, combined with Timeloop's accounting (halo, depth, bypass) and the GEMM paper's finding that 97% utilisation is not the optimum, says the report should carry a soft score and the minimal split factor, not just a verdict.

Two things remain open. The notes could not verify Graphene's tensors-of-tensors notation, CuTe's oversampling rule for partial tiles, or how GSPMD pads uneven shards, so the ragged-edge semantics in this report rest on LEGO and Shardy only. And no surveyed source measures the performance or usability trade-off between homogeneous and heterogeneous inner splits; that is an experiment distlayout is positioned to run, since on AIR the cost is countable (segments, arms, packet ids) before any hardware is touched.
